# 부하 테스트 계획 보고서

> 작성 목적: 콘서트 예약 시스템의 안정적인 서비스 운영을 위한 배포 스펙 결정 및 병목 구간 사전 파악

---

## 1. 부하 테스트 배경 및 목적

### 왜 부하 테스트가 필요한가?

콘서트 예약 시스템은 **특정 시간에 트래픽이 폭발적으로 몰리는 구조**입니다.
인기 콘서트 오픈 시점에는 수천 명의 유저가 동시에 접근하며, 이 구간에서의 장애는 매출 손실과 사용자 이탈로 직결됩니다.

배포 전에 다음 질문에 답을 얻어야 합니다:
- 현재 시스템은 **동시에 몇 명까지** 처리할 수 있는가?
- **어느 지점에서 응답 속도가 느려지거나 오류가 발생**하는가?
- 안정적인 운영을 위해 **서버에 얼마만큼의 자원(CPU/Memory)을 할당**해야 하는가?

---

## 2. 부하 테스트 대상 선정

### 핵심 대상: 좌석 예약 API

```
POST /api/reservations
POST /api/payments
```

**선정 이유:**
- 예약과 결제는 **트랜잭션을 포함한 쓰기 연산**으로 DB 부하가 가장 큼
- 콘서트 오픈 시 수천 명이 동시에 같은 좌석에 요청 → **동시성 충돌** 발생 가능 구간
- 실제 장애 시 비즈니스 임팩트가 가장 큰 엔드포인트

### 보조 대상: 대기열 발급 및 랭킹 조회

```
POST /api/queue/token
GET  /api/concerts/rankings
```

**선정 이유:**
- 대기열 토큰은 예약 전 모든 유저가 거치는 **입구 트래픽** 지점
- 랭킹 조회는 Redis 기반의 읽기 연산으로 **캐시 효율 검증** 가능

## 3. 테스트 시나리오

### 시나리오 A — 점진적 부하 증가 (Ramp-up)

| 단계 | 가상 유저 | 지속 시간 | 목적 |
|------|-----------|-----------|------|
| 워밍업 | 10명 | 30초 | JVM warm-up |
| 부하 증가 | 10 → 100명 | 1분 | 임계점 탐색 |
| 최대 부하 유지 | 100명 | 2분 | 안정성 확인 |
| 부하 감소 | 100 → 0명 | 30초 | 회복 확인 |

**목표 지표:**
- 응답 시간 p95 ≤ 500ms
- 에러율 ≤ 1%
- 처리량(TPS) ≥ 50

### 시나리오 B — 스파이크 테스트 (콘서트 오픈 시뮬레이션)

| 단계 | 가상 유저 | 지속 시간 | 목적 |
|------|-----------|-----------|------|
| 평상시 | 10명 | 30초 | 기준 수립 |
| 스파이크 | 10 → 500명 | 10초 | 급격한 유입 시뮬레이션 |
| 유지 | 500명 | 1분 | 최대 부하 처리 여부 확인 |
| 회복 | 500 → 0명 | 30초 | 정상 복귀 확인 |

**목표 지표:**
- 스파이크 구간 에러율 ≤ 5%
- 스파이크 종료 후 30초 내 응답 시간 정상화

### 시나리오 C — 배포 스펙 탐색 (리소스 제한 조절)

동일한 부하(100명 동시 접속)에서 아래 스펙별 성능 비교:

| 스펙 | CPU | Memory |
|------|-----|--------|
| 최소 | 0.5 core | 512MB |
| 권장 | 1 core | 1GB |
| 여유 | 2 core | 2GB |

## 4. 테스트 환경

```
로컬 환경 (Docker)
├── Application (Spring Boot JAR)  → docker-compose.app.yaml 리소스 제한 적용
├── MySQL 8.0                      → docker-compose.yml
└── Redis                          → 기존 설정
```

**부하 생성 도구:** k6 (JavaScript 기반, 경량 HTTP 부하 테스트 도구)
